## 一、设计范围与核心流程

本次实验只设计一条可独立交付的核心流程：用户从首页进入新对弈或摆放局面，系统校验局面和走法，调用本地中国象棋引擎返回候选着法，展示评价与简短解释，对局结束后生成关键节点复盘和练习建议。

**本阶段纳入：**桌面入口、棋盘交互、规则校验、引擎适配器、结构化解释、复盘摘要、本地 JSON 保存、错误与人工确认状态。  
**本阶段不纳入：**联网匹配、账号/排行榜、社交系统、云端棋谱社区、语音课程和移动端适配。

## 三、2.2 技术选型与架构决策

### 3.2.1 候选方案比较

| 方案 | 熟悉程度 | 实现成本 | AI/引擎接入 | 测试与打包 | 结论 |
|---|---|---|---|---|---|
| Python + PySide6 + JSON | 较高，适合个人快速开发 | 低 | 可用子进程调用本地引擎，也可接 HTTP | pytest、PyInstaller 生态成熟 | **选用** |
| C# + WPF + SQLite | 中等 | 中 | 桌面 UI 和本地数据库强 | Windows 打包好，但学习成本更高 | 作为后备方案 |
| Electron + TypeScript | 中等 | 高 | 接口灵活 | 打包体积和前端工程量偏大 | 不作为 MVP 首选 |

### 3.2.2 最终技术选择

- **语言与界面：**Python 3.11 + PySide6。原因是能快速实现桌面窗口、信号槽和跨模块测试。
- **体系结构：**轻量分层 + Ports and Adapters。界面层不直接调用引擎；领域层不依赖具体 UI；引擎、解释器和文件存储都通过适配器替换。
- **数据保存：**MVP 使用本地 JSON 文件，按 game_id 保存一局完整记录；后续数据量明显增大时再迁移 SQLite。
- **AI 接入：**优先本地中国象棋引擎进程；解释默认模板化，LLM 仅作为可选适配器，不作为规则和胜负判定器。
- **打包：**PyInstaller 生成 Windows 单文件或目录包；本地引擎作为可配置资源目录随包发布。

### 3.2.3 架构决策记录（ADR）

**ADR-01：采用分层 + 端口适配器**

- **问题：**引擎协议和界面逻辑变化时，怎样不影响规则和复盘代码？
- **考虑方案：**单文件脚本、MVC、分层 + 端口适配器。
- **选择：**分层 + 端口适配器。
- **理由：**规则可独立单元测试；引擎可用 Mock 替换；未来从本地引擎切换到其他引擎时影响较小。
- **不足：**文件和接口数量增加，对个人项目有一定样板代码成本。

**ADR-02：本地优先，AI 结果必须经过程序校验**

- **问题：**模型或引擎失败时，如何避免展示虚假评价并保护棋谱隐私？
- **考虑方案：**全部使用云模型、全部使用本地引擎、引擎本地 + 解释可选云端。
- **选择：**引擎本地 + 模板解释为默认，云端 LLM 为可选。
- **理由：**断网可用、费用可控、棋谱默认不上传；合法性和真值留在确定性代码中。
- **不足：**本地引擎安装和性能差异需要在设置页提示；生成式解释质量有限。

**ADR-03：MVP 使用 JSON，SQLite 作为替代方案**

- **问题：**如何在开发初期简单保存并调试对局？
- **考虑方案：**纯内存、JSON、SQLite。
- **选择：**JSON 文件，接口保持 Repository 抽象。
- **理由：**无需数据库安装，便于查看、备份和测试；数据量小且为单用户。
- **替代方案：**若保存超过 20 局、出现查询性能或并发需求，迁移 SQLite，不改变上层接口。

## 五、2.4 数据、接口与核心流程设计

### 5.1 数据模型

**图3 数据模型图。** Game 是一次对局的聚合根，Move 保存用户和 AI 的每个半回合，AnalysisPoint 记录评价变化与人工确认标记，ReviewSummary 保存复盘结果。棋谱内容属于用户数据，默认只在本地 JSON 中保存；human_review_required 是安全边界字段，必须在 UI 中明确展示。

源文件：实验3设计文件/diagrams/03-数据模型图.mmd

**主要约束：**

- game_id、move_id、point_id、review_id 全局唯一；
- ply 从 1 开始递增，legal=false 的尝试不得写入正式 Move；
- from_square 与 to_square 必须经过规则模块校验；
- evaluation 允许为空，表示引擎失败或尚未分析；
- human_review_required=true 时，解释页面必须显示人工确认提示；
- 保存失败时保留内存状态，不覆盖上一次可回读文件。

### 5.2 主要接口

**表4 核心接口设计**

| 接口 | 提供模块 | 调用方 | 输入 | 输出 | 失败处理 |
|---|---|---|---|---|---|
| POST /games（本地服务语义） | GameService | 首页/对弈页 | side、difficulty、initial_position | game_id、board_state | 参数不完整返回 INVALID_GAME |
| POST /games/{id}/moves | GameService | 对弈页 | from、to、expected_turn | move_id、legal、next_turn | 非法走法不写入 Move，返回 ILLEGAL_MOVE |
| POST /games/{id}/analysis | EngineAdapter | GameService | board_state、time_limit | candidates、evaluation、pv | 超时返回 ENGINE_TIMEOUT，允许重试 |
| POST /games/{id}/explanation | ExplanationAdapter | 对弈页/复盘页 | structured_facts | text、labels、human_review_required | LLM 失败切换模板 |
| POST /games/{id}/finish | ReviewService | 对弈页 | moves、analysis_points | key_points、advice | 部分分析也可生成，标记 partial=true |
| GET/PUT /games/{id} | FileRepository | 首页/复盘页 | game JSON | saved game / status | 磁盘失败提示并保留内存数据 |

**正常调用示例：**POST /games/g-001/analysis 输入合法局面、执红和 3000 毫秒上限；输出 1—3 个候选着法、评价值和主变化。  
**错误调用示例：**缺少将帅时返回 INVALID_POSITION，提示补充或重新摆局，engine_called=false。

### 5.3 核心流程图

**图4 核心流程图。**正常路径是“合法局面—合法落子—引擎应答—解释—结束复盘”；非法局面、非法走法和引擎失败都回到可恢复状态；多解或长变例会显式进入人工确认分支。

源文件：实验3设计文件/diagrams/04-核心流程图.mmd

### 6.3 界面状态清单

| 状态 | 触发 | 界面反馈 | 用户下一步 |
|---|---|---|---|
| 空数据 | 首次打开或没有历史对局 | 显示空状态说明和开始按钮 | 新建对弈/摆局 |
| 加载中 | 请求引擎或解释器 | 禁止重复提交，显示思考状态 | 等待、取消或重试 |
| 非法输入 | 局面或走法不符合规则 | 标出错误格、错误码和修正建议 | 修正或返回 |
| 引擎失败 | 超时、进程异常、结果不可解析 | 保留棋盘和已走棋步，不展示虚假评价 | 重试或手动复盘 |
| 人工确认 | 多解、长变例或置信不足 | 显示候选列表和“需要人工确认” | 选择练习方向或继续 |
| 成功完成 | 结束对局并生成摘要 | 展示关键节点和建议 | 再次练习、导出、返回 |

## 九、实验小结

本次实验将实验2的产品需求转换为可指导开发的设计基线。系统采用轻量分层 + 端口适配器，普通程序负责规则、状态、保存和错误处理，本地象棋引擎负责候选着法和评价，模板或可选 LLM 只负责解释草稿，并且所有结果都要经过程序校验或用户确认。

数据设计以 Game 为聚合根，围绕 Move、AnalysisPoint 和 ReviewSummary 保存一次对局的完整学习反馈；接口设计覆盖开始、落子、分析、解释、结束复盘和本地读写。三个关键原型分别覆盖入口、核心任务和结果反馈，并明确空数据、加载、错误、人工确认和重新操作状态。通过需求—设计追踪和一致性检查，确保 US、FR、AC 能够追溯到模块、数据、接口和界面。
